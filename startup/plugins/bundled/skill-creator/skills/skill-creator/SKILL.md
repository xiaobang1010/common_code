# Skill Creator

一个用于编写和迭代优化本地技能的技能。

整体流程：

- 弄清技能应该做什么、大致怎么做
- 写一版草稿
- 用 2-3 个真实的测试提示词试试
- 和用户一起看输出，修改
- 重复直到技能足够好

你的工作是判断用户在流程的哪一步，帮他们推进。他们可能说"我想要一个做 X 的技能"（从头开始），也可能已经有草稿了（跳到评估/迭代）。灵活一点——如果用户说"随便聊聊，不用正式评估"，那就那样做。

## 和用户沟通

使用这个技能的人从经验丰富的技能作者到第一次尝试的新手都有。注意上下文线索。有疑问时，简短解释一下术语（"评估提示词就是你发给模型看看技能怎么响应的测试消息"），别假设对方熟悉。

## 创建技能

### 捕捉意图

先理解用户想要什么。如果当前对话已经有值得捕获的工作流（比如用户手动做了几次同样的事然后说"把这个变成技能"），先从对话历史里提取答案——他们用了什么工具、什么步骤顺序、做了什么修正、输入输出格式。在写草稿前和用户确认缺失的信息。

有用的问题：

1. 这个技能应该让模型能做什么？
2. 什么时候触发？什么用户措辞或场景？
3. 期望的输出格式是什么？
4. 有没有示例输入输出来锁定行为？

### 技能放在哪里

系统在以下目录发现技能（优先级从高到低）：

- `<project>/.agent/skills/<name>/SKILL.md`（项目级，最高优先级）
- `~/.agent/skills/<name>/SKILL.md`（用户级）

**默认在 `.agent/skills/` 下创建新技能**——这是标准的技能存放位置。项目级路径适合只对当前项目有意义的技能；用户级路径适合你想在所有地方使用的个人技能。

插件也可以提供技能（放在插件的 `skills/` 子目录下，source 标记为 "plugin"）。

### 编写 SKILL.md

每个技能是一个目录，包含一个带 YAML frontmatter 和 markdown 正文的 `SKILL.md`：

```text
my-skill/
├── SKILL.md          （必填）
└── （可选）
    ├── references/   （模型按需阅读的额外文档）
    ├── scripts/      （模型可调用的辅助脚本）
    └── assets/       （模板、夹具等）
```

必填 frontmatter：

- `name` — 技能标识符。小写 kebab-case，1-64 字符。必须和目录名匹配。
- `description` — 这个技能什么时候触发、做什么。这是主要的触发信号——技能做什么和在什么场景下用都写这里，不写正文里。模型倾向于少触发技能，所以描述要写得稍微强势一点：与其写"如何为内部数据建仪表盘"，不如写"如何快速为内部数据建仪表盘。当用户提到仪表盘、数据可视化、内部指标或想展示任何公司数据时使用——即使他们没明说'仪表盘'。"

可选 frontmatter 字段：

- `when-to-use` — 何时使用的详细场景说明
- `allowed-tools` — 技能激活时额外授予的工具权限（列表）
- `disable-model-invocation` — 设为 true 则只允许用户斜杠命令触发，禁止模型自动调用
- `user-invocable` — 设为 false 则禁止用户斜杠命令触发
- `paths` — gitignore 风格的路径匹配模式，条件式技能（只有模型触碰到匹配文件时才激活）

### 渐进式披露

系统分三层加载技能：

1. **元数据**（name + description）始终在上下文中。保持简短。
2. **SKILL.md 正文**只在技能触发时加载。目标 500 行以内。
3. **附属文件**（references/、scripts/、assets/）按需读取。大小不限。

如果正文变长了，把领域特定细节拆到参考文件里，让 SKILL.md 告诉模型什么时候去读。例如：

```text
cloud-deploy/
├── SKILL.md            （工作流 + 选择逻辑）
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```

SKILL.md 里写"如果目标是 AWS，先读 references/aws.md 再继续。"

### 写作风格

用祈使句（"编辑前先读文件"）。当规则不明显时解释为什么——现代模型在理解原因时遵循得更好。如果你发现自己在大写 MUST 和 NEVER，那通常说明规则需要更好的解释而不是更响亮的强制。

示例胜过规则。如果技能产生结构化输出，包含一个格式的字面示例。如果应该用特定工具，展示调用方式。

### 测试提示词

写完草稿后，想 2-3 个真实的测试提示词——用户实际会打的那种，有具体文件路径、列名、随意措辞甚至错别字。和用户分享："这里有几个我想试的。有什么要加或改的吗？"

然后运行它们：加载草稿技能，把测试提示词发给模型，检查结果。一个一个来，每次和用户一起看结果。

## 审查草稿

对每个测试提示词：

1. 确保草稿技能在磁盘上系统能发现的位置（上面列的目录之一）。
2. 在新的一轮对话中，把测试提示词给模型。让描述自动触发技能，或用 `/skill-name` 强制加载。
3. 和用户一起看结果。技能触发了吗？输出符合预期吗？哪里跑偏了？

同时注意结果和过程：如果技能导致模型做了一堆无用功（反复读同一个文件、写临时脚本、原地打转），技能可能过度规定或不清楚。那是该精简的信号，不是加更多规则。

---

## 改进技能

这是循环的核心。你运行了测试提示词，用户审查了输出，现在让技能更好。

如何思考改进：

1. **从反馈中泛化。** 你和用户在几个例子上迭代是为了速度，但技能需要对你们都没见过的输入也能工作。如果某个顽固问题怎么针对性修改都不行，试试换一种框架或比喻，而不是堆更多约束。过度拟合的琐碎规则和压迫性的 MUST 会让技能随时间变差。

2. **保持提示词精简。** 删掉不起作用的部分。如果模型在技能鼓励下浪费 token 做无用功，删掉相关指导看看会怎样。

3. **解释为什么。** 今天的模型在给定上下文时推理得很好。即使用户的反馈简短或沮丧，也要弄清他们真正想要什么，把那种理解传达到指令中。重新框定通常比更多强制更有效。

4. **寻找重复工作。** 如果每次测试运行都独立写了同样的辅助脚本或采取了同样的多步方法，把脚本打包到 `scripts/` 下让技能指向它。写一次而不是让模型每次重新发明。

然后循环：

1. 应用改进。
2. 重新运行测试提示词。
3. 给用户看新输出。
4. 继续直到他们满意或进一步修改不再有帮助。

---

## 更新现有技能

如果用户想更新已有的技能而不是创建新的：

- 保留原始 `name` 和目录名。如果已安装的技能是 `research-helper`，更新后还是 `research-helper`，不是 `research-helper-v2`。
- 如果已安装技能路径是只读的（比如随官方插件缓存分发），把技能复制到可写的用户位置如 `~/.agent/skills/<name>/`，在那里编辑，用户优先级发现会覆盖原始版本。
- 不同路径的同名技能作为独立安装保留；路径是安装身份。
