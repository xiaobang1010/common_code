# Spec 驱动开发模式

把"边想边写"变成"先对齐再执行"。通过三份 markdown 文档锁定需求、拆解任务、定义验收标准，
执行时状态自动流转，让复杂任务可追踪、可审查、可暂停恢复。

## 何时使用

**适用：**
- 从零搭建新系统/模块/应用（需求范围大、架构决策多）
- 大规模重构、技术栈迁移（涉及大量文件和依赖）
- 多人/多轮协作的复杂项目（需要对齐理解）
- 高稳定性要求的核心逻辑（需要详尽验收清单）
- 用户明确要求 spec 模式、先规划、要任务清单

**不适用：**
- 改个 bug、加个小功能、调样式 → 直接做，别套三件套
- 纯查询、解释代码、读文件 → 不需要规划文档

判断不准时，倾向直接问用户："这个任务要不要走 spec 模式（先生成规划文档再执行）？"

## 路径管理（贯穿全程）

spec 三件套统一存放在项目根目录的 `.trae/specs/<任务名>/` 下。这个路径是整个流程的锚点，确定后所有读写都基于它。

**确定项目根：** 取当前工作目录；若当前目录在某个 git 仓库内，取 git 仓库根目录。确认后告知用户 spec 将存放在 `<项目根>/.trae/specs/`。

**目录结构：**
```
<项目根>/.trae/specs/<任务名>/
  spec.md
  tasks.md
  checklist.md
```

**路径记忆：** 确定任务名后，在后续所有步骤中始终使用这个完整路径读写文件，不要凭记忆拼凑、不要切换目录。读取文件时用完整路径；更新状态时定位到具体文件的行。

## 三阶段流程

### 阶段 1：前置检查与生成

#### 1.1 前置检查（生成前必须执行）

这一步避免覆盖已有工作、避免生成的 spec 脱离项目实际。

1. **扫描现有 spec 目录**：用 glob 检查 `<项目根>/.trae/specs/` 下已有哪些任务目录。
   - 如果已存在与当前需求同名的目录 → 不要覆盖。读取其中的三件套，转为「续接」流程：向用户报告当前进度，从第一个未完成 task 继续。
   - 如果存在相关但不同名的任务（如之前做过类似模块）→ 读一眼其 spec.md，参考已有的技术决策，避免重复规划。

2. **读取项目上下文**：为了让 spec 贴合项目实际，生成前先了解项目：
   - 读 `package.json` / `go.mod` / `pom.xml` / `Cargo.toml` 等，确认技术栈和依赖
   - 看一眼项目顶层目录结构，了解模块划分
   - 如果用户需求涉及现有代码，读相关文件
   把这些信息作为生成 spec.md 技术方案的依据，不要凭空编造技术选型。

#### 1.2 确定任务名

从用户需求提炼一个 kebab-case 英文名，如 `user-auth-system`、`refactor-api-layer`、`add-payment-module`。简短、达意、可做目录名。此时锁定 spec 路径 = `<项目根>/.trae/specs/<任务名>/`。

#### 1.3 生成三个文件

按 `references/file-templates.md` 的模板，用实际内容填充（别留占位符），写入 spec 路径：
- `spec.md` — 需求大纲（EARS 风格：Why/What Changes/Impact + ADDED/MODIFIED/REMOVED Requirements，需求用 SHALL 句式 + Scenario WHEN/THEN）
- `tasks.md` — 执行任务列表（分组、有序、带 checkbox 状态，文末含 Task Dependencies 显式依赖与可并行标注）
- `checklist.md` — 验收清单（可检验的验收项，带 checkbox）

文档语言跟随用户对话语言（中文对话写中文）。tasks.md 和 checklist.md 的 checkbox 初始全为 `- [ ]`。

#### 1.4 暂停等确认（关键）

生成完三件套后**必须暂停**，不要直接开始写代码。明确告诉用户：
- 三个文件的完整路径
- spec.md 的核心要点摘要（2-3 句）
- tasks.md 的任务数量和分组
- 然后问："请检查文档，确认后我开始执行；或告诉我需要修改的地方。"

这一步让用户有机会修正方向，避免跑偏后返工。

### 阶段 2：审查与修改

用户可能：
- 直接说"确认"/"开始"→ 进入阶段 3
- 提修改意见 → 读取对应文件，只改用户指出的部分（别推翻重写），改完再次暂停确认
- 自己手动编辑了文件 → 重新读取文件内容，按最新版本执行

### 阶段 3：执行与状态联动

确认后按 `tasks.md` 的顺序逐项执行。**每完成一个 task，必须立即写回文件状态，再开始下一个 task**——这不是可选步骤，是 spec 模式的核心价值：让进度可追踪、可暂停恢复。

#### 执行循环

对 tasks.md 中每一个 `- [ ]` 任务，按顺序：

1. **执行任务**：写代码、改文件、跑命令等，完成该 task 描述的工作。

2. **更新 tasks.md**：用 Edit 把该 task 所在行的 `- [ ]` 改成 `- [x]`。定位方式：匹配该任务的编号和描述文本，精确替换那一行的 checkbox。

3. **更新 checklist.md**：扫一遍 checklist.md 的所有 `- [ ]` 项，把**因这个 task 完成而确实已满足**的验收项改成 `- [x]`。
   - 判断规则：该验收项描述的能力/行为，是否已经因为这个 task 的完成而实际具备。是 → 勾选；否 → 保持未勾选。
   - 一个 task 可能满足 0 个、1 个或多个验收项；一个验收项也可能需要多个 task 才能满足。
   - 不要为了"凑进度"而勾选尚未真正满足的项。验收项是质量底线，必须诚实。

4. **继续下一个** `- [ ]` 任务，回到步骤 1。

#### 完成判定

当 tasks.md 所有任务都是 `- [x]` 时：
1. 最后通读 checklist.md，确认所有验收项都是 `- [x]`。
2. 若有未勾选的验收项 → 说明有 task 没覆盖到该验收点，补做相应工作，补勾。
3. 全部通过后告诉用户任务完成，附上 spec 路径供其查阅。

#### 异常处理

执行中发现：
- 任务列表有遗漏 → 补充新 task 到 tasks.md（用下一个编号），继续
- 某个 task 做不了/需要重新设计 → 在 tasks.md 标注并暂停，问用户怎么办
- 发现 spec.md 的技术方案需要调整 → 更新 spec.md 对应部分，同步受影响的 tasks，暂停确认

## 续接已存在的 spec

当 `.trae/specs/<任务名>/` 已存在三件套时（用户中途回来、换会话继续、或前置检查发现同名任务）：
1. 读取三个文件，理解当前进度（看 tasks.md 哪些已勾选、checklist.md 哪些已通过）
2. 告诉用户当前进度（已完成 X/Y 个任务，checklist 通过 Z/W 项）
3. 询问：继续执行剩余任务，还是调整规划？
4. 确认后从第一个未完成 task 继续，走阶段 3 的执行循环，无需重新生成

## 文件格式约定

三个文件都用标准 markdown，checkbox 用 `- [ ]` / `- [x]`。任何 markdown 渲染器都能显示状态，不依赖特殊工具。完整模板和字段说明见 `references/file-templates.md`，生成文件前先读它。

## 与项目集成

- `.trae/specs/` 可纳入版本控制，作为项目知识资产长期保留
- 多人协作时，spec 文档是单一事实来源
- 任务完成后，spec.md 仍可作为该模块的设计文档留存
